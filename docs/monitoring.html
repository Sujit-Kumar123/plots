Kubernetes Monitoring

Full observability for all 6 Plots microservices — request metrics, Kafka consumer lag, PostgreSQL health, and Redis performance — via a single Helm chart deployment.

kube-prometheus-stack Prometheus 2.x Grafana 11.x Alertmanager Helm 3 Kubernetes 1.27+

Stack components

One Helm release installs the full observability stack. Three infrastructure exporters are deployed separately into plots-system so they can read existing K8s secrets.

Architecture

Every FastAPI service exposes /metrics on its existing port via prometheus-fastapi-instrumentator. Prometheus Operator reads ServiceMonitor custom resources to discover scrape targets — no manual scrape_configs required.

Installation

Run the install script from the project root to deploy everything in one shot. The steps below explain what the script does.

One-command install: bash k8s/monitoring/install.sh
1
Add the Helm repository
Registers prometheus-community so Helm can pull the chart.
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
2
Install kube-prometheus-stack
Deploys Prometheus, Grafana, Alertmanager, node-exporter, and kube-state-metrics into the monitoring namespace. Uses custom values from k8s/monitoring/helm-values.yaml.
helm upgrade --install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --create-namespace \
  --values k8s/monitoring/helm-values.yaml \
  --wait --timeout 10m
3
Create the plots-system namespace
The exporters and app services live here. Must exist before applying subsequent resources.
kubectl apply -f k8s/namespace.yaml
4
Deploy infrastructure exporters
Kafka, PostgreSQL, and Redis exporters deployed into plots-system. They read credentials from the plots-secrets Secret.
kubectl apply -f k8s/monitoring/exporters.yaml
5
Apply ServiceMonitors
Creates ServiceMonitor CRDs for all 6 app services and the 3 exporters. Prometheus Operator picks these up automatically — no restart needed.
kubectl apply -f k8s/monitoring/servicemonitors.yaml
6
Verify pod status
Check both namespaces. See the expected output and explanations below.
kubectl get pods -n monitoring
kubectl get pods -n plots-system

Helm configuration

All chart behaviour is controlled through k8s/monitoring/helm-values.yaml. The file is passed to helm upgrade --install via --values and overrides the upstream chart defaults. Below is a tour of every block and the reasoning behind each setting.

Chart: prometheus-community/kube-prometheus-stack  ·  Release name: monitoring  ·  Namespace: monitoring

Prometheus

The prometheus.prometheusSpec block configures the Prometheus StatefulSet that the Prometheus Operator creates.

prometheus:
  prometheusSpec:
    retention: 15d             # keep metrics for 15 days
    scrapeInterval: 15s        # poll targets every 15 s (default 60 s)
    evaluationInterval: 15s   # evaluate alert rules every 15 s

    # Watch ServiceMonitors in ALL namespaces.
    # Without these three settings Prometheus only watches ServiceMonitors
    # that have the label  release: monitoring  AND live in the monitoring namespace.
    serviceMonitorSelectorNilUsesHelmValues: false
    serviceMonitorSelector: {}
    serviceMonitorNamespaceSelector: {}

    # Same for PodMonitors (not used yet, but keeps the door open).
    podMonitorSelectorNilUsesHelmValues: false
    podMonitorSelector: {}
    podMonitorNamespaceSelector: {}

    storageSpec:
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 50Gi  # PVC created automatically by the operator

    resources:
      requests:
        memory: 512Mi
        cpu: 250m
      limits:
        memory: 2Gi
        cpu: 1000m
KeyValueWhy
retention15d Balances storage cost against enough history to investigate weekly trends. Increase to 30d in production.
scrapeInterval15s Fast enough to catch short request spikes on the FastAPI services without heavy CPU overhead.
serviceMonitorSelectorNilUsesHelmValuesfalse When true (the default), Prometheus only discovers ServiceMonitors that share the Helm release label. Setting false combined with empty selectors makes it watch all ServiceMonitors in all namespaces.
serviceMonitorSelector: {}match all Empty label selector = no filter = every ServiceMonitor is discovered, including the ones in monitoring that point at plots-system.
serviceMonitorNamespaceSelector: {}all namespaces Allows Prometheus Operator to read ServiceMonitor CRDs from namespaces other than its own.
storage: 50GiPVC Prometheus data survives pod restarts. Adjust based on cardinality and retention period.

Dashboard providers

The dashboardProviders block registers a file-based provider. Grafana's sidecar container watches a ConfigMap for dashboard JSON files and writes them to the path directory at runtime. The plots folder name becomes the folder in the Grafana UI.

      apiVersion: 1
      providers:
        - name: plots         # logical provider name — used as a key below
          orgId: 1
          folder: Plots       # folder name shown in the Grafana sidebar
          type: file
          disableDeletion: false
          editable: true
          options:
            path: /var/lib/grafana/dashboards/plots  # where JSON is written

Alertmanager

The alertmanager block configures storage and the routing tree that determines what happens when Prometheus fires an alert.

alertmanager:
  enabled: true
  alertmanagerSpec:
    storage:
      volumeClaimTemplate:
        spec:
          accessModes: ["ReadWriteOnce"]
          resources:
            requests:
              storage: 5Gi   # persists silences and notification history

  config:
    global:
      resolve_timeout: 5m   # mark alert resolved if not re-fired within 5 min

    route:
      group_by: ["alertname", "namespace", "job"]  # deduplicate similar alerts into one notification
      group_wait:      30s   # wait 30 s before sending first notification (batches rapid-fire alerts)
      group_interval:   5m   # wait 5 min before re-notifying about the same group
      repeat_interval: 12h   # re-notify every 12 h while alert stays active
      receiver: "null"       # default: drop (no notification) — add Slack/email below
      routes:
        - matchers:
            - alertname =~ "InfoInhibitor|Watchdog"  # silence built-in heartbeat alerts
          receiver: "null"

    receivers:
      - name: "null"         # the null receiver discards all notifications

    inhibit_rules:
      # If a Critical alert fires, suppress Warning/Info for the same pod.
      # Prevents a flood of warning noise when a service is fully down.
      - source_matchers:
          - severity = critical
        target_matchers:
          - severity =~ warning|info
        equal: [alertname, namespace, pod]
Routing keySettingEffect
group_by[alertname, namespace, job]Multiple pods firing the same alert are grouped into one notification instead of one per pod.
group_wait30sBuffers the first 30 seconds so rapid successive firings become one message.
group_interval5mOnce a group is notified, Alertmanager waits 5 min before sending another update for that same group.
repeat_interval12hIf the alert is still firing 12 hours later, send another reminder.
inhibit_rulescritical → suppresses warningAvoids alert storms: when a pod is completely down (critical), its per-endpoint warning alerts are suppressed.

Custom alert rules — PromQL explained

All four rules are grouped under additionalPrometheusRulesMap.plots-alerts.groups[0] and evaluated against the plots-system namespace. Prometheus evaluates them every evaluationInterval (15 s).

ServiceDown  Critical · for: 1m

up{namespace="plots-system"} == 0

The up metric is set to 1 by Prometheus after each successful scrape and 0 on failure. This rule fires if any scrape target in plots-system has been unreachable for a full minute — catching both crashed pods and misconfigured ServiceMonitors.

HighErrorRate  Warning · for: 5m

sum(rate(http_requests_total{namespace="plots-system", status=~"5.."}[5m])) by (job)
/
sum(rate(http_requests_total{namespace="plots-system"}[5m])) by (job)
> 0.05

Numerator: per-second rate of 5xx responses over the last 5-minute window, summed per service (job label).

Denominator: per-second rate of all requests, same window.

Threshold: > 0.05 = more than 5% of requests are failing. Uses rate() (not irate()) for a smoother signal that ignores momentary spikes.

HighP99Latency  Warning · for: 5m

histogram_quantile(
  0.99,
  sum(rate(http_request_duration_seconds_bucket{namespace="plots-system"}[5m])) by (job, le)
) > 2

http_request_duration_seconds_bucket is the histogram emitted by prometheus-fastapi-instrumentator. Each bucket has an le (less-than-or-equal) upper bound label.

rate(...)[5m] turns the cumulative bucket counters into a per-second rate, then histogram_quantile(0.99, ...) estimates the 99th percentile duration from those rates.

Fires when the estimated P99 exceeds 2 seconds for 5 consecutive minutes. Grouped by job so you know which service is slow.

KafkaConsumerLag  Warning · for: 5m

kafka_consumergroup_lag_sum > 10000

kafka_consumergroup_lag_sum is emitted by kafka-exporter. It represents the total number of messages in a Kafka topic that have been produced but not yet consumed by a consumer group.

A lag above 10,000 messages sustained for 5 minutes indicates a consumer is falling behind — either overwhelmed, crashed, or blocked. The alert labels carry consumergroup and topic so you can identify which service is lagging.

Applying changes to a running release

After editing helm-values.yaml, re-run the same helm upgrade command — no need to uninstall first. Helm diffs the rendered manifests and applies only what changed.

helm upgrade monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --values k8s/monitoring/helm-values.yaml
Changes to additionalPrometheusRulesMap or dashboards take effect within one scrape interval (≤ 15 s) without restarting Prometheus. Changes to prometheusSpec.resources or grafana.adminPassword require the respective pod to restart — Helm handles this automatically via a rolling update.

Instrumentator(excluded_handlers=["/health.*", "/metrics"]).instrument(app).expose(app)

For chat-service and plot-service, /metrics was added to the InternalAuthMiddleware._SKIP frozenset so Prometheus can scrape without the x-internal-secret header.

Troubleshooting

Kubernetes cluster unreachable

Docker Desktop Kubernetes is not enabled or hasn't finished starting. Open Docker Desktop → Settings → Kubernetes → Enable Kubernetes → Apply & Restart. Wait ~2 minutes, then verify with kubectl cluster-info.

namespace "plots-system" not found

The application namespace must exist before the exporters are applied. Run kubectl apply -f k8s/namespace.yaml first, then re-apply exporters and ServiceMonitors.

node-exporter: CrashLoopBackOff on Docker Desktop Windows

node-exporter tries to bind-mount /proc and /sys from the host OS. Docker Desktop on Windows runs Kubernetes inside a Linux VM where those paths are not exposed in the way node-exporter expects, causing it to crash immediately.

Fix: disable the host root filesystem mount in helm-values.yaml:

prometheus-node-exporter:
  hostRootFsMount:
    enabled: false

Then apply: helm upgrade monitoring prometheus-community/kube-prometheus-stack --namespace monitoring --values k8s/monitoring/helm-values.yaml

This setting is already included in the current helm-values.yaml. If you installed before this fix was added, run the upgrade command above.

postgres-exporter / redis-exporter: CreateContainerConfigError

Both exporters reference plots-secrets as a secretKeyRef source for credentials. If this Secret does not exist in plots-system, Kubernetes cannot inject the environment variables and refuses to start the container.

kubectl describe pod -n plots-system -l app=postgres-exporter
# Events: ... Error: secret "plots-secrets" not found

This is expected when the app services haven't been deployed yet. The pods will automatically recover (no manual restart needed) as soon as plots-secrets is created by the app deployment process.

To verify once secrets exist: kubectl get secret plots-secrets -n plots-system

kafka-exporter: Error / CrashLoopBackOff

kafka-exporter connects to kafka:9092 on startup. If Kafka is not yet deployed to plots-system, the connection is refused and the container exits with an error.

This is expected before the app services are deployed. Kubernetes will keep restarting the pod (backoff increases from 10 s up to 5 min). Once Kafka is running at kafka:9092, the next restart attempt will succeed automatically.

install.sh: namespace "plots-system" not found on exporters step

If you see this error even though install.sh has the namespace creation step, it means the script ran with an older cached version, or the kubectl apply -f k8s/namespace.yaml call failed silently on first run. Fix by running the steps manually:

kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/monitoring/exporters.yaml
kubectl apply -f k8s/monitoring/servicemonitors.yaml

Kubernetes cluster unreachable on first install.sh run

Docker Desktop Kubernetes takes ~2 minutes to become fully ready after enabling it. The first helm upgrade --install call may fail with the server could not find the requested resource. Wait until kubectl cluster-info shows the control plane URL, then re-run bash k8s/monitoring/install.sh — Helm is idempotent and safe to re-run.

kubectl cluster-info
# Kubernetes control plane is running at https://kubernetes.docker.internal:6443

Prometheus targets show state DOWN

App services haven't been deployed to plots-system yet, or their pods are not running. Verify with kubectl get pods -n plots-system. Also confirm each Kubernetes Service has the label app: <name> — all six service YAML files in k8s/services/ were updated with this label.

Grafana shows "No data"

Go to Grafana → Connections → Data Sources → Prometheus → click Test. If the test passes, wait 1–2 scrape intervals (15–30 seconds) and refresh the dashboard time range.

chat-service or plot-service /metrics returns 403

Both services run InternalAuthMiddleware which blocks requests without x-internal-secret. The /metrics path must be in the _SKIP frozenset in app/common/internal_auth.py for both services. Rebuild the Docker image if the change isn't reflected in the running container.

helm: command not found in Git Bash

Helm was installed to %USERPROFILE%\bin but Git Bash hasn't reloaded PATH. Close and reopen Git Bash, then verify with helm version.

The curl | bash installer may also fail on Git Bash on Windows because it requires sudo. This is safe to ignore — if helm version works, Helm is correctly installed.

Suspend without deleting

Scale every component to zero replicas. Nothing is deleted — all Deployments, StatefulSets, PVCs, ConfigMaps, Secrets, and RBAC rules remain intact. Scaling back up restores the full stack with all historical data.

Fully reversible. PVCs are untouched so Prometheus metrics and Grafana state survive the suspension and are immediately available when you resume.

Suspend everything

# ── Stop monitoring namespace: Grafana + kube-state-metrics ──────────────────
kubectl scale deployment --all --replicas=0 -n monitoring

# ── Stop Prometheus and Alertmanager StatefulSets ────────────────────────────
kubectl scale statefulset --all --replicas=0 -n monitoring

# ── Stop infrastructure exporters in plots-system ────────────────────────────
kubectl scale deployment kafka-exporter postgres-exporter redis-exporter \
  --replicas=0 -n plots-system

Stop node-exporter (DaemonSet)

DaemonSets cannot be scaled to zero directly. Instead patch in a nodeSelector that matches no node — this causes Kubernetes to evict all DaemonSet pods without deleting the DaemonSet itself.

kubectl patch daemonset monitoring-prometheus-node-exporter \
  -n monitoring \
  -p '{"spec":{"template":{"spec":{"nodeSelector":{"suspend":"true"}}}}}'

Verify all pods stopped

kubectl get pods -n monitoring
# No resources found in monitoring namespace.  ← expected

kubectl get pods -n plots-system | grep exporter
# No output  ← expected

Resume — scale back up

# ── Restart monitoring namespace ──────────────────────────────────────────────
kubectl scale deployment --all --replicas=1 -n monitoring
kubectl scale statefulset --all --replicas=1 -n monitoring

# ── Restart exporters ─────────────────────────────────────────────────────────
kubectl scale deployment kafka-exporter postgres-exporter redis-exporter \
  --replicas=1 -n plots-system

# ── Restore node-exporter DaemonSet ──────────────────────────────────────────
kubectl patch daemonset monitoring-prometheus-node-exporter \
  -n monitoring \
  --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
After resuming, Prometheus re-attaches to its PVC and replays the existing WAL (write-ahead log). All metrics stored before the suspension are visible in Grafana immediately. There is a gap in the timeline for the period the stack was suspended — this is expected.

Restart from Docker

Use this when you stopped everything with docker stop $(docker ps -q), restarted your machine, or Docker Desktop restarted on its own. Follow the steps in order — Kubernetes must be fully ready before scaling the monitoring stack.

Data is safe. Docker stop does not delete volumes or Kubernetes PVCs. All Prometheus metrics and Grafana state from before the stop are still there.
1
Start Docker Desktop
Open Docker Desktop from the Start menu or system tray. Wait until both status indicators in the bottom-left turn green — Docker engine running and Kubernetes running. This takes about 2 minutes.
# Verify Docker is up
docker info

# Verify Kubernetes is up
kubectl cluster-info
# Expected: Kubernetes control plane is running at https://kubernetes.docker.internal:6443
If kubectl cluster-info shows errors, Kubernetes is still starting. Wait 30 seconds and try again — do not proceed to the next step until it returns the control plane URL.
2
Check which namespaces exist
Confirm that both namespaces survived the Docker restart.
kubectl get namespace monitoring plots-system
# NAME           STATUS   AGE
# monitoring     Active   Xh
# plots-system   Active   Xh
If either namespace is missing, the cluster state was wiped (this can happen on a full Docker Desktop reset). In that case skip to Step 6 — Full reinstall.
3
Scale monitoring namespace back up
Restarts Prometheus, Grafana, Alertmanager, and kube-state-metrics.
kubectl scale deployment --all --replicas=1 -n monitoring
kubectl scale statefulset --all --replicas=1 -n monitoring
4
Scale exporters back up
Restarts Kafka, PostgreSQL, and Redis exporters in plots-system.
kubectl scale deployment kafka-exporter postgres-exporter redis-exporter \
  --replicas=1 -n plots-system
5
Restore node-exporter DaemonSet
Only needed if you previously applied the suspend patch. Removes the dummy nodeSelector so the DaemonSet can schedule pods again.
kubectl patch daemonset monitoring-prometheus-node-exporter \
  -n monitoring \
  --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
If the patch returns "nodeSelector not found" that is fine — it means the DaemonSet was never patched and is already running normally.
6
Verify all pods are running
Wait ~60 seconds after scaling, then check. Prometheus and Grafana take the longest to become Ready.
kubectl get pods -n monitoring
# NAME                                                     READY   STATUS
# alertmanager-monitoring-kube-prometheus-alertmanager-0   2/2     Running
# monitoring-grafana-*                                     3/3     Running
# monitoring-kube-prometheus-operator-*                    1/1     Running
# monitoring-kube-state-metrics-*                          1/1     Running
# monitoring-prometheus-node-exporter-*                    1/1     Running
# prometheus-monitoring-kube-prometheus-prometheus-0       2/2     Running

kubectl get pods -n plots-system
# kafka-exporter-*      1/1   Running  (only if Kafka is deployed)
# postgres-exporter-*   1/1   Running  (only if plots-secrets exists)
# redis-exporter-*      1/1   Running  (only if plots-secrets exists)
7
Open Grafana
Run in a separate terminal and keep it open while browsing.
kubectl port-forward svc/monitoring-grafana 3000:80 -n monitoring
Open http://localhost:3000  ·  Username: admin  ·  Password: changeme-in-prod

Full reinstall (if namespaces are gone)

If Docker Desktop was fully reset and the monitoring or plots-system namespaces no longer exist, run the install script from scratch. It is safe to run multiple times.

# From the project root in Git Bash
bash k8s/monitoring/install.sh
A full reinstall after a cluster reset creates fresh PVCs. Any Prometheus metrics or Grafana dashboards from before the reset are gone. This is only relevant if Docker Desktop was reset — a normal restart preserves everything.

Teardown

Three levels of teardown are available depending on whether you want to pause monitoring temporarily, remove the stack entirely, or nuke everything including stored data.

GoalCommands below
Stop port-forwards only (keep cluster running)Stop port-forwards
Remove everything, keep PVC dataSoft teardown
Remove everything including all stored metricsFull teardown

Stop port-forwards

Port-forwards are just local processes — closing the terminal window is enough. To kill them programmatically:

# PowerShell — kill all kubectl port-forward processes
Get-Process kubectl -ErrorAction SilentlyContinue | Stop-Process -Force
# Git Bash / Linux
pkill -f "kubectl port-forward"

The cluster keeps running untouched. Restart port-forwards any time with the commands in the Accessing UIs section.

Soft teardown — remove stack, keep PVC data

Uninstalls the Helm release and deletes the custom resources applied manually. PVCs are not deleted by default, so all historical metrics and Grafana state survive and can be re-attached if you reinstall.

1
Delete ServiceMonitors
Remove the 9 ServiceMonitor CRDs so Prometheus stops trying to scrape.
kubectl delete -f k8s/monitoring/servicemonitors.yaml
2
Delete infrastructure exporters
Removes the Kafka, PostgreSQL, and Redis exporter Deployments and Services from plots-system.
kubectl delete -f k8s/monitoring/exporters.yaml
3
Uninstall the Helm release
Removes Prometheus, Grafana, Alertmanager, node-exporter, kube-state-metrics, and all related ConfigMaps, Secrets, and RBAC. PVCs are left intact.
helm uninstall monitoring --namespace monitoring
4
Verify removal
kubectl get all -n monitoring
# Should return: No resources found in monitoring namespace.

kubectl get pvc -n monitoring
# PVCs are still present — this is expected for a soft teardown.
To reinstall later, simply run bash k8s/monitoring/install.sh again. Helm will recreate all resources and the Prometheus StatefulSet will re-attach to the existing PVC, recovering all historical metric data.

Full teardown — remove everything including stored data

Irreversible. Deleting PVCs permanently destroys all stored metrics, Grafana dashboards, and Alertmanager silences. There is no undo.

Run the soft teardown steps above first, then delete the PVCs and namespace:

# 1. Delete the Helm release + exporters + ServiceMonitors (steps 1-3 above)
kubectl delete -f k8s/monitoring/servicemonitors.yaml
kubectl delete -f k8s/monitoring/exporters.yaml
helm uninstall monitoring --namespace monitoring

# 2. Delete PVCs (Prometheus 50 Gi + Grafana 10 Gi + Alertmanager 5 Gi)
kubectl delete pvc --all -n monitoring

# 3. Delete the monitoring namespace itself
kubectl delete namespace monitoring
# Confirm everything is gone
kubectl get namespace monitoring
# Error from server (NotFound): namespaces "monitoring" not found
The plots-system namespace and application services are not affected by either teardown. Only the monitoring components are removed.

Remove individual components

To disable a specific component without touching the rest, scale its Deployment to zero or disable it in helm-values.yaml and re-apply.

ComponentRemove command
kafka-exporter only kubectl delete deploy,svc kafka-exporter -n plots-system
postgres-exporter only kubectl delete deploy,svc postgres-exporter -n plots-system
redis-exporter only kubectl delete deploy,svc redis-exporter -n plots-system
Grafana (keep Prometheus) Set grafana.enabled: false in helm-values.yaml, then helm upgrade
Alertmanager (keep Prometheus) Set alertmanager.enabled: false in helm-values.yaml, then helm upgrade
node-exporter (keep everything else) Set nodeExporter.enabled: false in helm-values.yaml, then helm upgrade
One ServiceMonitor (stop scraping one service) kubectl delete servicemonitor <name> -n monitoring
