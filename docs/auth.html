Authentication & Authorization

Complete reference for how users register, log in, refresh tokens, reset passwords, authenticate via SSO, and how the API Gateway enforces role-based permissions on every request.

All auth routes live in auth-service and are proxied through the API Gateway at http://api-gateway:8000.

Public vs Protected
Public paths bypass JWT validation entirely — they are whitelisted in middleware.py under _PUBLIC_PATHS. All other paths require a valid access_token cookie or Authorization: Bearer <token> header. Missing token → 401. Valid token but insufficient permission → 403.

Token Design

Two JWTs are issued on every successful auth event. Both are HS256-signed with AUTH_SECRET_KEY and stored as httpOnly cookies so JavaScript cannot read them directly.

Access Token

type
"access"
sub
User UUID (string)
role
Role short_name e.g. "member"
exp
30 minutes from issuance
Cookie
access_token · httpOnly · maxAge 1800s

Refresh Token

type
"refresh"
sub
User UUID (string)
role
Role short_name
exp
7 days from issuance
Cookie
refresh_token · httpOnly · maxAge 604800s
Role stored as short_name, not name
The JWT role claim stores the Roles.short_name field (e.g. "member", "admin") — not the display Roles.name (e.g. "Member"). The gateway uses this value to look up permissions via /api/auth/internal/role-permissions, which queries WHERE Roles.short_name = ?.

Session Architecture

The auth-service maintains a sessions table in PostgreSQL. Tokens are never stored raw — only their SHA-256 hashes are persisted. This means a stolen token dump cannot be directly replayed.

access_token_hash
SHA-256 of the access JWT
refresh_token_hash
SHA-256 of the refresh JWT (unique index)
expires_at
Created + 7 days (session lifetime, not token lifetime)
revoked_at
NULL while active; timestamped when revoked (logout, refresh rotation, password change)
ip_address
Client IP at session creation
device_type
"web" / "mobile" / "tablet" (parsed from User-Agent)
One active session per user
A partial unique index uq_active_session_per_user on (user_id) WHERE revoked_at IS NULL enforces that each user has at most one live session at a time. Logging in while already logged in revokes the old session first.

Session Validation (Two-layer)

On every protected request the gateway validates the session in two steps:

1
Redis cache check

Key session:<token_hash>. If cached "1" (valid) or "0" (invalid), return immediately. TTL is 60 seconds — avoids a DB round-trip on every request.

2
Auth-service fallback

Cache miss → POST /api/auth/internal/validate-session with { token_hash }. Checks Sessions table: access_token_hash = ? AND revoked_at IS NULL AND expires_at > now. Result is cached for 60 s.

Registration

POST /api/auth/register public AUTH_EMAIL_ENABLED=true required 
{
  "email": "alice@example.com",
  "password": "SecurePass123!",
  "fname": "Alice",        // optional
  "lname": "Smith"         // optional
}
1
Duplicate check

Query users WHERE email = ? AND is_deleted = false. Raises 409 Conflict if found.

2
Assign default role

Fetches the role with short_name = "member" and sets user.role_id. If no such role exists in the DB (unseeded), role_id is NULL — user gets no permissions until seeded.

3
Create user + profile

Password is hashed with bcrypt (hash_password()). A linked Profiles row is created with fname/lname.

4
Issue tokens

_build_tokens(user) reads user.role.short_name for the JWT role claim. Both a 30-min access token and 7-day refresh token are created.

5
Create session

Inserts into sessions: both token hashes, expires_at = now + 7 days, client IP, device type.

6
Set cookies + return

Backend sets Set-Cookie: access_token=…; refresh_token=… on the response. Frontend server action also calls cookies().set() to ensure httpOnly cookies are stored. Returns { user, tokens }.

Success Response

{
  "success": true,
  "data": {
    "user": { "id": "uuid", "email": "alice@example.com", "role": { "short_name": "member" }, ... },
    "tokens": { "access_token": "eyJ...", "refresh_token": "eyJ..." }
  }
}

Login

POST /api/auth/login public AUTH_EMAIL_ENABLED=true required 
{
  "email": "alice@example.com",
  "password": "SecurePass123!"
}
1
User lookup + password verify

Fetches user by email. Verifies bcrypt hash. Returns 401 for either wrong email or wrong password (same error message — no enumeration).

2
Active check

If user.is_active = false, raises 401 "Account is deactivated".

3
Revoke previous session

Finds any session with user_id = ? AND revoked_at IS NULL and sets revoked_at = now(). Enforces single-session policy.

4
Update last_login

Sets user.last_login = now() for audit purposes.

5
Issue tokens + create session

Same as registration steps 4–6. New session row inserted with fresh token hashes.

Device type detection
The User-Agent header is parsed to categorize the device as "mobile", "tablet", or "web". This is stored on the session row for future session management features.

Token Refresh

POST /api/auth/refresh public token rotation — old refresh_token is revoked

Accepts the refresh token in either the JSON body (server-to-server) or the refresh_token cookie (browser requests):

// Server-to-server (Next.js server action)
POST /api/auth/refresh
Content-Type: application/json
{ "refresh_token": "eyJ..." }

// Browser (credentials: 'include' — reads httpOnly cookie automatically)
POST /api/auth/refresh
// No body needed — backend reads request.cookies.get("refresh_token")
1
Extract refresh token

Tries JSON body first (body.get("refresh_token")). Falls back to request.cookies.get("refresh_token"). Returns 401 if neither provides a token.

2
Decode & type-check JWT

Decodes the token. If signature is invalid, expired, or type != "refresh", raises 401 "Invalid refresh token".

3
Session lookup

Queries sessions WHERE refresh_token_hash = SHA256(token) AND revoked_at IS NULL. Also checks session.is_valid (not expired). Returns 401 "Session expired or revoked" if not found.

4
Revoke old session

Sets session.revoked_at = now() — the old session is immediately dead. Any concurrent requests using the old access token will fail session validation within 60 s (Redis TTL).

5
Issue new tokens + new session

Both a new access token and a new refresh token are generated. A new session row is inserted with fresh hashes. Old IP and device_type are carried over.

6
Set cookies + return both tokens

Backend response includes Set-Cookie for both. Frontend server action calls cookies().set() for both access_token (maxAge 1800s) and refresh_token (maxAge 604800s) so the browser receives updated cookies.

Token Rotation — both cookies must be updated
The backend revokes the old refresh_token on every refresh call and issues a brand-new one. If only the access_token cookie is updated but not the refresh_token cookie, the next refresh attempt sends the now-revoked old token and returns 401 — effectively logging the user out. The frontend's refreshServerToken() persists both new tokens.

Frontend Refresh Mutex

If five concurrent server actions all receive a 401 simultaneously, only one call to /api/auth/refresh must be made. The _refreshInFlight Map in server-api.ts implements a server-side mutex keyed by the current refresh_token value:

// Simplified logic in server-api.ts
const existing = _refreshInFlight.get(refreshToken)
if (existing) return existing           // reuse in-flight promise

const promise = doRefresh()             // single HTTP call
_refreshInFlight.set(refreshToken, promise)
promise.finally(() => _refreshInFlight.delete(refreshToken))
return promise                          // all 5 callers await the same promise

Logout

POST /api/auth/logout auth required
1
Identify user

Gateway decodes the access token and sets request.state.user_id. The get_current_user dependency fetches the user from the DB.

2
Revoke active session

logout_user(user_id) sets revoked_at = now() on the user's active session. Subsequent requests with the old access token will fail session validation within 60 s.

3
Clear cookies

Backend sets Set-Cookie: access_token=; Max-Age=0; refresh_token=; Max-Age=0. Frontend server action also calls cookies().delete() for both.

Forgot Password

POST /api/auth/forgot-password public AUTH_EMAIL_ENABLED=true required 
{ "email": "alice@example.com" }
1
Silent user lookup

Queries for the email. If no user exists, the response is identical to success — no email enumeration.

2
Generate reset token

generate_reset_token() creates a cryptographically random raw token. Its SHA-256 hash is stored in password_reset_tokens with expires_at = now + 1 hour.

3
Send email

Calls the notification service with the reset URL: {FRONTEND_URL}/reset-password?token={raw_token}. Uses the password_reset email template.

4
Debug mode

If settings.debug = true, the reset_url is returned in the response body so it can be used without a real email server during development.

Reset token storage
Only the hash of the reset token is stored in the database (hash_reset_token() — a dedicated hash function separate from hash_token()). The raw token travels only through the email link, never persisted in plain text.

Reset Password

POST /api/auth/reset-password public 
{ "token": "<raw token from email link>", "new_password": "NewPass456!" }
1
Token lookup

Hashes the raw token (hash_reset_token(raw_token)) and queries password_reset_tokens WHERE token_hash = ? AND is_used = false AND is_deleted = false. Returns 422 if not found.

2
Expiry check

If expires_at < now(), raises 422 "Reset token has expired".

3
Update password

Sets user.hashed_password = hash_password(new_password).

4
Revoke session + mark used

Sets reset.is_used = true (one-time use). Revokes the user's active session — forcing re-login with the new password.

Change Password

POST /api/auth/change-password auth required AUTH_EMAIL_ENABLED=true required 
{ "current_password": "OldPass123!", "new_password": "NewPass456!" }

Verifies the current password first. If correct, hashes the new password and saves it. The active session is revoked — the user must log in again (or the frontend can immediately call /api/auth/login with the new password).

SSO — Google OAuth 2.0

GET /api/auth/google GET /api/auth/google/callback AUTH_GOOGLE_ENABLED=true required
1
Initiate

Browser visits GET /api/auth/google. GoogleAuthService.generate_auth_url() builds a Google OAuth2 consent URL with the configured GOOGLE_CLIENT_ID and GOOGLE_OAUTH_REDIRECT_URI. Browser is redirected to Google.

2
User consents on Google

User approves the requested scopes (email, profile). Google redirects to GOOGLE_OAUTH_REDIRECT_URI with ?code=AUTH_CODE&state=….

3
Callback: exchange code

GET /api/auth/google/callback?code=… — GoogleAuthService.authenticate_with_google(code, ip) exchanges the auth code for an access + refresh token from Google's token endpoint.

4
Fetch user info from Google

Uses the Google access token to fetch the user's id, email, name from Google's userinfo endpoint.

5
Upsert user in DB

If google_id exists in DB → link existing account. If email matches → link Google to existing account. Otherwise → create new user with auth_source = "google", is_verified = true (email verified by Google), hashed_password = NULL.

6
Issue tokens, redirect to dashboard

Same token issuance flow as email login. Backend sets auth cookies on a 302 → /dashboard redirect response.

hashed_password is NULL for pure SSO users
Users created via Google have hashed_password = NULL. They cannot log in via email/password and must use the SSO flow. To allow both methods, users can set a password via Change Password after linking.

SSO — Azure AD OAuth 2.0

GET /api/auth/azure GET /api/auth/azure/callback AUTH_AZURE_ENABLED=true required

Identical flow to Google OAuth but uses Azure AD endpoints. Configured via AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, AZURE_TENANT_ID (default "common" for multi-tenant), and AZURE_OAUTH_REDIRECT_URI.

User model stores azure_id and azure_refresh_token for account linking. auth_source is set to "azure" for newly created Azure users.

Roles

Roles are the bridge between users and permissions. Each user has at most one role (users.role_id FK). Roles are seeded in the database and managed via the roles API.

Role Model

id
UUID (primary key)
name
Display name, e.g. "Member", "Admin"
short_name
Machine-readable slug stored in JWT, e.g. "member", "admin", "superadmin"
description
Human description of the role
role_permissions
M:N relationship → role_permissions join table
superadmin wildcard
The role with short_name = "superadmin" is resolved locally in the gateway — it always receives frozenset({"*"}) without a DB round-trip. The wildcard "*" passes every require_permission() check.

Role Assignment API

MethodPathDescription
GET/api/auth/rolesList all roles with their permissions
POST/api/auth/rolesCreate a new role
PATCH/api/auth/roles/{id}Update name / short_name / description
DELETE/api/auth/roles/{id}Soft-delete (fails if users still assigned)
POST/api/auth/roles/{role_id}/assign/{user_id}Assign role to a user
DELETE/api/auth/roles/unassign/{user_id}Remove user's role
JWT role is cached in the token
The role claim is baked into the JWT at login time. Changing a user's role in the DB does not affect live sessions — the user must log out and back in to receive a token with the new role. Redis permission cache TTL is 5 minutes (_PERM_CACHE_TTL = 300).

Permissions

Permissions are fine-grained codes in the format resource:action. They are assigned to roles and enforced at the gateway router level.

Gateway Middleware

SessionValidationMiddleware in services/api-gateway/app/middleware.py runs on every inbound request before it reaches any route handler. It validates the token, populates request state, and fetches the user's permission set.

Decision Chain

Public path?

If the path is in _PUBLIC_PATHS (login, register, refresh, health…) or starts with a public prefix (/api/auth/google, /api/auth/azure, /api/auth/internal/) → skip all checks, call next().

Extract token

Reads from Authorization: Bearer <token> header first, then falls back to the access_token cookie.

No token?

Returns 401 "Authentication required" for all non-public paths. This ensures the frontend's 401 handler triggers a token refresh attempt rather than receiving an ambiguous 403.

Validate session

SHA-256 hashes the token → checks Redis key session:<hash>. Cache miss → POST auth-service /api/auth/internal/validate-session. If valid = false → 401 "Session expired or revoked". Result cached for 60 s.

Session invalid?

401 "Session expired or revoked" — session was revoked (logout, refresh rotation, password change) or exceeded 7-day lifetime.

Decode JWT

jose.jwt.decode(token, secret_key, algorithms=["HS256"]). Validates signature and the exp claim. Any JWTError (bad signature, expired, malformed) → 401 "Invalid token".

Set request state

Populates request.state.user_id (from sub), request.state.user_payload (full claims), request.state.user_role (from role claim).

Fetch permissions

_fetch_role_permissions(role_name): superadmin → inline {"*"}. Others: Redis key perms:<role> (5 min TTL) → auth-service /api/auth/internal/role-permissions. Result stored in request.state.user_permissions: frozenset[str].

Route handler runs

Route handlers that require a specific permission call require_permission("profile:read") from dependencies.py. This checks the frozenset against the code plus wildcards. If absent → 403 "Missing permission: profile:read".

Public Path Whitelist

_PUBLIC_PATHS = {
    "/api/auth/login",
    "/api/auth/register",
    "/api/auth/forgot-password",
    "/api/auth/reset-password",
    "/api/auth/refresh",
    "/health",
    "/health/ready",
    "/docs", "/redoc", "/openapi.json",
}
_PUBLIC_PREFIXES = (
    "/api/auth/google",
    "/api/auth/azure",
    "/api/auth/internal/",   # internal service-to-service calls
)

Permission Check Logic

# dependencies.py — require_permission("profile:read")
perms: frozenset = getattr(request.state, "user_permissions", frozenset())

if "*" in perms:           return  # superadmin — pass
if permission in perms:    return  # exact match
if "profile:*" in perms:  return  # resource wildcard
if "*:read" in perms:     return  # action wildcard
if "*:*" in perms:        return  # full wildcard

raise HTTPException(403, "Missing permission: profile:read")
Redis caching reduces auth-service load
With Redis running, permission lookups add ~0.5 ms (cache hit) instead of ~5–15 ms (auth-service HTTP call). Session validation similarly. If Redis is unavailable, the middleware falls through to HTTP — it does not fail open or closed.

Frontend Token Flow

The Next.js frontend uses server actions exclusively — no API calls from browser JavaScript. All token handling happens server-side.

Login / Register

loginAction() and registerAction() in lib/services/server/auth.ts call the backend directly from the Next.js server. They extract data.tokens from the JSON response and call cookies().set() to write httpOnly cookies — bypassing the browser entirely. The browser never sees the raw token values.

Authenticated Requests

serverFetch() and cqrsFetch() in lib/server-api.ts read the access_token cookie on the server and forward it as Cookie: access_token=… in the request to the API Gateway.

Auto-Refresh on 401

1
Server action gets 401

Access token expired. The gateway returns 401 because the JWT exp has passed (signature decode raises JWTError).

2
Mutex check

refreshServerToken() reads the current refresh_token cookie. Checks _refreshInFlight Map — if another concurrent action already started a refresh for this token, the promise is reused. Prevents multiple simultaneous refreshes.

3
POST /api/auth/refresh

Sends { "refresh_token": "<value>" } in the JSON body to the backend via BACKEND_INTERNAL_URL.

4
Persist BOTH new tokens

Extracts body.data.access_token and body.data.refresh_token. Both are persisted via cookies().set() — access_token with maxAge: 1800, refresh_token with maxAge: 604800. Critical because the backend rotates the refresh token on every refresh.

5
Retry original request

serverFetch() retries once with the new access token. The _retryToken parameter prevents infinite retry loops on a second 401.

6
Refresh failed → throw

If refreshServerToken() returns null (refresh token expired or revoked), serverFetch throws "Session expired. Please log in again." which bubbles to the component.

Why both cookies must be updated
The backend performs refresh token rotation — it revokes the old refresh_token session and issues a completely new one. If the frontend only saves the new access_token but not the new refresh_token, the next refresh attempt (after another 30 min) will send the now-revoked old refresh token → backend returns 401 → user is logged out unexpectedly.
